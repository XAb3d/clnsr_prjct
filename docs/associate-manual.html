AB3 Credit Bureau — Internal Operations Guide

Cleanser App: Associate Manual

A full walkthrough of the day-to-day workflow — cleaning a file, understanding why records get rejected, rescuing and re-registering them, and generating the reports you need to send. Written for the person doing the work, not the person who built the tool.

01Welcome

The Cleanser app takes the raw files financial institutions submit each month — Individual (IND) and Business (BUS) credit records — and gets them ready for loading into the bureau's system. It checks every field against Bank of Ghana reporting standards, fixes what it safely can, and sets aside anything it can't be sure about so a human makes the final call.

This manual walks through that whole cycle: uploading a file, reading what came back, understanding why something didn't pass, fixing it by hand when needed, and telling the system about that fix so it doesn't ask again next month.

Who this is for
Associates running monthly cleaning cycles for subscriber institutions. No coding knowledge needed — everything here is about what you click and what it means, not how it's built.

02Before You Start

What you need

A submission file from a subscriber institution (ADB, UMB, or others), in the standard template format, named with the subscriber's code as the first part of the filename — for example ADB2026_07_IND.xlsx.

The one filename rule that actually matters
The system reads the text before the first underscore in the filename to figure out which subscriber the file belongs to. Whatever you do to a filename afterward — adding _CLEAN, _RESCUED, a date, whatever — is fine, as long as that first segment stays exactly as it was on the original submission. Change that part, and the system may resolve to the wrong subscriber, or fail to resolve one at all.

The two working views

The main screen has two modes you'll switch between, using the buttons at the top:

Top of screen
CLEANING A FILE REFERENCE / REGISTER RECORDS

CLEANING A FILE is where you'll spend most of your time — this is the monthly cycle. REFERENCE / REGISTER RECORDS is a separate, less-frequent action, covered in Chapter 7.

03Cleaning a File

  1. Make sure you're on the CLEANING A FILE tab.
  2. Upload the subscriber's submission file using the file picker.
  3. Click Run Cleanser. Processing time depends on file size — larger files (thousands of records) take longer. Don't close the tab while it's running.
  4. When it finishes, a row of counters appears showing what happened to the file (covered in the next chapter).
  5. Download the CLEAN and UNLOADABLE (UNL) sheets from the output workbook.
What "cleaning" actually does
Every field in every record gets checked and, where possible, corrected — phone number formats, date formats, ID number formats, address fields, and so on. Records that pass every check go to CLEAN. Records that fail one or more checks the system isn't confident enough to auto-fix go to UNLOADABLE for a human to look at.

05Why a Record Was Rejected

Every record that lands in UNL has a reason attached — usually visible as an error note on the specific field that failed. Some of the more common and less obvious ones are worth understanding in detail:

Disbursement date "doesn't match previous submission"

For most facility types, a disbursement date that doesn't match what's on file from a prior month is a real red flag — it usually means a data entry error. But overdraft facilities are the exception: they legitimately get redrawn on new dates every month, sometimes more than once in the same submission. The system now understands this — as of the most recent update, overdraft records with a new (but genuine) disbursement date are no longer wrongly flagged. If you still see this on an overdraft record, look closely; it may be a real discrepancy worth checking.

What changed
Before this fix, a facility's disbursement-date history could get collapsed down to just one remembered date internally, so even a genuinely valid earlier date could get wrongly flagged. That's fixed — the system now checks a new date against the full history for that facility, not just the last one it happened to remember.

Same Customer ID, different Ghana Card numbers

If the same Customer ID shows up linked to two different GHA (Ghana Card) numbers across records — even if one is filed under "National ID" and the other under "Voter ID" or any other ID column — the system flags this as a conflict. A person only has one Ghana Card number, so two different ones under the same Customer ID means something is wrong: either a typo in one of the ID fields, or these are actually two different people who've been given the same Customer ID by mistake.

FieldValue
CustomerID38849
NatIDNum (record 1)GHA-712066477-4
VotersIDNum (record 2)GHA-721943099-6

This exact pattern — same Customer ID, two different GHA numbers, under two different ID columns — is what triggers the flag. Note that this rule is specific to GHA-format numbers; a mismatch between two non-Ghana-Card ID types under the same Customer ID does not trigger it, since only the Ghana Card is guaranteed unique per person.

How to resolve it
Check the original submission source. If it's a typo, correct the wrong GHA number and the record can be manually rescued (Chapter 6). If it genuinely looks like two different people were submitted under one Customer ID, that needs to go back to the subscriber for correction — don't guess which one is right.

06Manually Rescuing Records

Sometimes a record in UNL just needs a human correction — a typo fixed, a format cleaned up, a genuine discrepancy resolved after checking the source. When that happens:

  1. Open the UNL sheet and find the record.
  2. Make the correction directly in the file (or in your working copy of it).
  3. Move the corrected record into the CLEAN sheet — add it as a new row there.
  4. Keep going until you've rescued everything you're confident about for this cycle.
This isn't the end of the story
A record you've manually rescued this way is now correct in this month's output — but the system's memory of what's "normal" for that customer doesn't know about your correction yet. Without the next step (Chapter 7), the exact same record could get flagged again next month. Don't skip it.

07Registering Records

This is how you tell the system "these records are correct, remember them" — so manually rescued records (and initial reference loads for a new subscriber) don't get flagged again in future months.

  1. Switch to the REFERENCE / REGISTER RECORDS tab.
  2. Upload your corrected CLEAN sheet — the one that now includes the records you manually rescued in Chapter 6.
  3. Click Register / Insert reference(s).
  4. Records in that file get registered into the reference database. Re-uploading the same file later won't create duplicates — it's safe to re-run if you're not sure whether something already went through.
Why one tab does two jobs
This same tab is also used for loading a brand-new subscriber's initial reference data for the first time. Both cases are really the same action underneath — "register these records as trusted" — the only difference is whether it's the first-ever load or a monthly correction.
Don't forget the filename rule
Same rule as Chapter 2 — keep the original subscriber-code prefix intact on whatever file you upload here. This tab uses the same filename parsing as everywhere else in the app.

08The Unloadable Log

After a cleaning run that produced UNL records, a new panel appears below the stats row, letting you generate the unloadable log for that file — the report you send back to the subscriber summarizing what was rejected and why.

Unloadable Log panel
Associate Subscriber Name Institution Type Comments

☐ Remember Subscriber Name / Institution Type for next time

Generate Unloadable Log
  1. Type in your name under Associate.
  2. The first time you generate a log for a given subscriber, fill in Subscriber Name and Institution Type — leave Remember... checked, and you won't need to type these again for that subscriber next month.
  3. Add anything relevant under Comments.
  4. Click Generate Unloadable Log — an Excel file downloads with the header row plus two rejection breakdown tables (Demographic Information and Financial Information).
Still manual for now
Date Emailed and Date Fixed are left blank in the generated log — fill these in yourself once you've actually sent it and once a correction comes back. Automating this end-to-end is planned but not built yet.
What's coming next
Right now, each run generates a fresh, standalone log file — it doesn't append to a running master log automatically, so copy the row in yourself if you're tracking history across months. Storing this log as a proper table in the database (instead of a one-off spreadsheet each time) is planned as a future improvement.

09Troubleshooting

"There is already an object named 'X' in the database"

This is a developer-side database error, not something you'll hit in normal day-to-day use of the app. If you see it, the app likely needs a database update from IT/development — it's not something to work around yourself.

The Unloadable Log panel isn't showing up

It only appears after a cleaning run that produced at least one UNL record, in the current session. If the file you ran was completely clean (no rejections), there's nothing to report, so the panel correctly stays hidden. Try a file you know has rejections to confirm it's working.

A record I registered still gets flagged next month

Double-check the filename prefix rule from Chapter 2/7 — if the subscriber code couldn't be resolved from the filename, the registration may not have gone where you expected. Also confirm you registered the corrected version of the record (post-rescue), not the original rejected one.

Something looks wrong and you're not sure why

Don't guess. Flag it to the development team with the filename, subscriber, and the specific record(s) in question — cross-record checks like the GHA card conflict rule are deliberately conservative, but they're not infallible, and a genuinely unusual case is worth a second pair of eyes.

10Glossary

CLEAN
Records that passed every check and are ready to load.
UNL / Unloadable
Records that failed one or more checks and need a human decision before they can be loaded.
Subscriber Code
The short code identifying a financial institution (e.g. ADB, UMB), derived from the leading part of a submission filename.
Reference Database
The system's memory of previously-trusted records, used to detect matches, duplicates, and mismatches on new submissions.
Overdraft Facility
A credit facility type that can legitimately be redrawn on new dates repeatedly — unlike a term loan, which has one disbursement date.
GHA Card / Ghana Card
Ghana's national identification number, uniquely assigned per person — format looks like GHA-XXXXXXXXX-X.
Manually Rescued Record
A record originally rejected to UNL, then corrected by hand and moved into the CLEAN output for that month.
Registering a Record
Uploading a record (via the REFERENCE / REGISTER RECORDS tab) so the system trusts it going forward, without re-running it through cleaning.
